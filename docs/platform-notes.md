# Browser platform notes for scanoficus

**Date: late 2026.** Source review, not physical-device certification; includes published Safari 27.0/27.1 notes. Minimum versions are API introductions, **not** recommended production versions. Hardware-dependent features must be tested on the active camera.

**Evidence labels:** **Verified** = inspected release notes, compatibility data, source or package/dataset records; **Reported** = bug-reporter observation, not a platform guarantee; **Recommendation** = engineering inference. WebKit `main` establishes implementation, not the first shipping OS containing it. Unknown minimums remain explicitly unknown.

## 1. Camera in installed iOS PWAs

**Verified:** standalone `getUserMedia()` works: WebKit [185448](https://bugs.webkit.org/show_bug.cgi?id=185448) records the fix and iOS 13.4 confirmation. This differs from [WKWebView support in iOS 14.3](https://webkit.org/blog/11353/mediarecorder-api/), exposed when the embedding application can capture natively. A WebKit third-party/in-app browser does **not** automatically inherit Safari's permission UI or permission storage: native permissions, host configuration and capture policy matter. The library cannot enable access a host refuses. See [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) and [version data](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json).

**Reported, not a persistence contract:** [280394](https://bugs.webkit.org/show_bug.cgi?id=280394) describes re-prompts on reload/relaunch and no Home Screen equivalent of persistent site Allow; comments describe differing behavior around 26.2 and 26.3.1(a). [327237](https://bugs.webkit.org/show_bug.cgi?id=327237) reports cold-launch re-prompts on 26.6.2 but contains incomplete test-result placeholders: it is not a conformance test. Historical hash-navigation issue [215884](https://bugs.webkit.org/show_bug.cgi?id=215884) is marked configuration changed; that does not establish resolution of every persistence problem. Android Chrome uses browser-managed permissions, also subject to one-time permission, revocation and OS policy.

**Reported lifecycle bugs:** [252465](https://bugs.webkit.org/show_bug.cgi?id=252465) concerns a PWA video element unable to play a camera stream; [275527](https://bugs.webkit.org/show_bug.cgi?id=275527) reports installed-PWA freezes on iOS 17.5.1. Neither proves all current devices fail or one workaround fixes all builds. No universally reliable minimum for background/resume behavior was established.

**Recommendation:** use visible `<video autoplay muted playsinline>`; request camera, not microphone. Model denial, muted/ended track, suspended page and stalled frames separately. On `visibilitychange`/`pagehide`, pause processing and normally release tracks; on return reacquire if needed, reassign `srcObject`, await `play()` and verify advancing frames. Offer user-triggered Restart Camera, Open in Safari and file import. Track release is best-effort resource management, **not** a guarantee against re-prompts. Do not recommend globally disabling camera protections.

## 2. Sharp still capture, resolution and camera selection

### APIs and realistic resolution

**Verified:** “Safari has no ImageCapture” is obsolete. [Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/) added Image Capture; [MDN per-method data](https://github.com/mdn/browser-compat-data/blob/main/api/ImageCapture.json) distinguishes `takePhoto` (18.4) from `grabFrame` (26). [Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) explicitly adds `grabFrame`. Chrome Android has both from 59, the `takePhoto(photoSettings)` argument from 60, and `getPhotoSettings` from 61.

[Chrome's Image Capture documentation](https://developer.chrome.com/blog/imagecapture/) distinguishes a video-resolution `grabFrame()` bitmap from photographic `takePhoto()` output, which can temporarily reconfigure the camera for higher resolution. Canvas `drawImage(video, ...)` cannot recover sensor pixels absent from the stream; a larger canvas merely upscales. Query `getPhotoCapabilities()` for photo dimensions and track capabilities for video ranges; inspect decoded output.

**Missing evidence:** no authoritative current per-device matrix establishes a universal maximum on iPhone or “typical Android.” **Do not promise 4K, 12 MP, 48 MP or native-camera-app quality.** 3840×2160 is 8.29 MP; 4032×3024 is 12.19 MP, not “4K video.” Native hardware modes do not establish browser access. [WebKit's camera backend](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/mediastream/cocoa/AVVideoCaptureSource.mm) enumerates video formats/frame-rate ranges and configures still-photo dimensions separately. [178109](https://bugs.webkit.org/show_bug.cgi?id=178109) documents resolution implementation work, not a device guarantee.

**Recommendation / unbenchmarked starting policy:** preview at ideal 1920×1080 with a modest frame-rate target; detect boundaries on a smaller image. Probe 3840×2160 on the actual camera only when useful; fall back to 1080p/720p. `ideal` may resolve lower; `exact` may reject. Read `getSettings()` and `videoWidth/videoHeight`. Higher resolution **can**, but does not inevitably, reduce delivered FPS because resolution/FPS are coupled hardware modes; it increases potential processing/bandwidth cost. Measure cadence, heat and still sharpness rather than asserting universal FPS or sensor-resolution ceilings.

### Still pipeline and bugs

1. Prefer capability-checked, error-handled `takePhoto()` on Safari 18.4+ and Android Chrome after validating actual size/quality. Wait for focus/exposure stabilization and low motion; more pixels cannot fix defocus.
2. **Serialize** photo capture and constraint changes. [Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/) fixes concurrent `takePhoto()`/`applyConstraints()` capture-session reconfiguration (174950018). Avoid overlapping calls especially on older Safari.
3. Fallback: optionally raise stream resolution briefly, wait for changed dimensions **and advancing settled frames**, capture, then restore preview constraints. Expect interruption, changed crop/aspect ratio or rejection. Re-detect boundaries on the still; do not blindly reuse preview pixel coordinates.
4. Always provide `<input type="file" accept="image/*" capture="environment">` and ordinary photo import. [MDN capture](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture) describes a hint, not guaranteed maximum resolution, lens or output format. Native camera UI can give better photographic processing, but that is a device-dependent expectation, not a web guarantee. Decode safely, normalize orientation and inspect dimensions. This also covers restrictive in-app hosts.

### Multiple cameras, close focus and zoom

**Verified/reported:** `facingMode: 'environment'` means rear-facing, **not** “physical standard-wide 1×.” [253186](https://bugs.webkit.org/show_bug.cgi?id=253186) records the fixed iOS 16.4-beta ultra-wide selection regression. [Safari 17.0](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/) separately fixes selection to use the system-preferred camera. The bug discussion describes close-focus problems on iPhone 13/14 Pro standard-wide cameras and native macro lens switching; those observations do not establish one numerical minimum-focus distance for every Pro model.

**Recommendation:** request permission, then `enumerateDevices()` and offer preview-based selection with exact `deviceId`. Do not rely on device order, English labels, persistent IDs after permission resets, or Android exposing all physical lenses; OEM/browser/camera-stack exposure varies. Start with the system default, then let users select another rear camera when focus/FOV is poor. Suggest backing away and cropping. Ultra-wide/macro can improve close focus while trading distortion/resolution.

**Verified implementation:** WebKit implemented zoom ([253646](https://bugs.webkit.org/show_bug.cgi?id=253646), March 2023); the backend sets AVFoundation `videoZoomFactor` and accounts for virtual cameras. Earliest shipped iOS version was not independently established. Chrome also exposes zoom on capable cameras. **Inference:** zoom on a logical/virtual camera may affect physical-lens selection, but the web API promises neither a particular lens nor native automatic macro switching. On a physical camera it may simply crop. Never assume `zoom: 2` selects the same lens across devices.

**Recommendation:** default to video + frame callback + downscale + transferred bitmap/worker. Keep one frame in flight, drop backlog and close bitmaps/frames on every path; bitmap creation is not guaranteed zero-copy. Provide ImageData/ArrayBuffer transfer and reduced-rate main-thread fallbacks. Track processors/WebCodecs are optional. Ordinary workers/transferables do not require cross-origin isolation; SharedArrayBuffer/WASM threads do, as a separate deployment choice.

## 5. iOS canvas, textures and memory pressure

**Verified correction:** “iOS canvas is always limited to 16,777,216 pixels” is stale. [271002](https://bugs.webkit.org/show_bug.cgi?id=271002) raised the iOS WebKit area limit in March 2024 from 4096² to **8192² = 67,108,864 pixels**. [CanvasBase.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/html/CanvasBase.cpp) checks **area**, not a universal 8192-pixel ceiling on each axis. First shipped Safari version was not established; do not equate landing date with release date. Backend/dimension/memory limits may be lower.

**Historical, not an entitlement:** [195325](https://bugs.webkit.org/show_bug.cgi?id=195325) documents aggregate canvas allocation failures including the “384 MB” warning. This is not a safe current per-tab/PWA memory budget. Decoded images, canvas/GPU copies, frame objects and WASM heaps compete for memory. iOS can terminate/reload web processes under memory pressure; installation provides no documented fixed larger heap.

**Texture sizes:** [Apple Metal feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) list 16,384-pixel 2D textures for many recent Apple GPU families, less for some older families. That is a **native hardware ceiling**, not verified Safari `MAX_TEXTURE_SIZE` for every recent iPhone. Query `MAX_TEXTURE_SIZE`, `MAX_RENDERBUFFER_SIZE` and viewport limits. No current physical-device measurement set was obtained; “all recent iPhones expose 16K” remains unverified. Android also requires runtime checks.

**Recommendation:** initially cap final output at ≤12 MP and use a 640–960-pixel detection long edge as **chosen budgets, not browser limits**. A 12 MP RGBA surface alone needs ~48 MB; 48 MP needs ~192 MB before copies. Reuse a small canvas pool; close bitmaps/frames, delete WASM matrices/GPU resources, revoke URLs and shrink discarded canvases (`width = height = 0`). Handle null contexts, encoding failures, context loss and restored pages. Tile large warps/downsample before allocating; do not discover limits by repeatedly allocating huge surfaces on users' phones. Persist completed pages incrementally.

## 6. Native OCR/detection and WebNN

- **BarcodeDetector:** [MDN data](https://github.com/mdn/browser-compat-data/blob/main/api/BarcodeDetector.json) lists Android Chrome **83+**, Safari **17+ behind the Shape Detection flag**. [Chrome documentation](https://developer.chrome.com/docs/capabilities/shape-detection) notes Android platform/service dependencies. Check constructor, `getSupportedFormats()` and actual operation; optional barcode capability only.
- **TextDetector/FaceDetector:** experimental/platform-specific Shape Detection is not portable OCR. No default production TextDetector support was verified on either target; no general document-quadrilateral/deskew/OCR JS API was found in reviewed shipping sources. Native iOS Live Text UI is not a JS OCR API. **Recommendation:** own boundary detection and load OCR separately, e.g. an appropriate WASM/ONNX engine.
- **WebNN:** [MDN data](https://github.com/mdn/browser-compat-data/blob/main/api/ML.json) lists no Safari implementation and Chrome 112+ behind a flag. The [2026 Chromium intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/5CWKSChYo98) excludes Android from the M147–149 trial due to immature implementation. [ChromeStatus](https://chromestatus.com/feature/5176273954144256) / [retrieved JSON](https://chromestatus.com/api/v0/features/5176273954144256) provides no shipped Android milestone. Flags/trials/desktop backends are not mobile production support. WebNN runs models; it does not supply an OCR model. **Recommendation:** do not require it.

## 7. WebGPU for later ML/OCR

**Verified:** [Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) ships WebGPU on iOS/iPadOS and other Apple platforms. [Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121) initially enables Android WebGPU on **Android 12+ Qualcomm or ARM GPUs**. The [Chrome support overview](https://developer.chrome.com/docs/web-platform/webgpu/overview) repeats this, but is dated August 2025: it does not establish every late-2026 GPU/driver combination. [Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/) has further WebGPU fixes/features; [27.1](https://webkit.org/blog/18486/webkit-features-for-safari-27-1/) does not announce a scanner-specific API change.

**Recommendation:** require a successful adapter/device request, not just `navigator.gpu`; validate model operators/limits and recover from device loss. Probe WKWebView rather than assuming host parity. Keep WASM CPU and, if justified, WebGL backends. Do not promise ML speedups without model/device benchmarks or include mandatory OCR/model runtime in the small scanner core.

## Recommended library strategy

1. **Portable core:** HTTPS camera + file import; reduced-resolution boundary detection and manual correction. Set a tested browser policy separately from API introduction versions.
2. **Capture adapter:** tested `takePhoto`, serialized operations, output/focus/orientation checks; settled high-resolution video and native file capture fallbacks. Re-detect still geometry.
3. **Lifecycle adapter:** permission/interruption/restart states, frame-stall watchdog, completed-scan persistence. Test Safari tab, installed PWA, WebKit third-party browser and restrictive in-app host separately.
4. **Bounded compute:** small detection frames, one worker task in flight, explicit cleanup/canvas reuse, recoverable context/device loss; no giant allocation probes.
5. **Optional acceleration:** worker canvas/WebGL2 when measured useful, realm-specific processor adapters, later WebGPU inference; no WebNN/native OCR requirement. Lazy-load OCR/models/PDF tools.
6. **Physical-device release gate:** older/newer and Pro/non-Pro iPhones plus Qualcomm and ARM/Mali Android. Record camera selection/capabilities, actual dimensions/FPS/photo size, focus, cold-start permission, lock/app-switch recovery and memory failures before publishing universal claims.

## Source quality, contradictions and remaining gaps

**Kept:** primary WebKit releases/bugs/implementation; MDN method-level data; Chrome documentation/ChromeStatus; project repositories, pinned package manifests and original dataset descriptions. Inline URLs are the finding-level source index.

**Contradictions:** aggregate [Can I Use ImageCapture](https://caniuse.com/imagecapture) summaries can imply no Safari support; specific WebKit releases and MDN methods establish newer support. Blanket “Safari cannot torch/zoom,” “16 MP canvas forever,” and “OpenCV is 30 MB” claims conflict with inspected evidence. Permission reports vary by build; no persistence guarantee is inferred. The 2023 implementation matrix and 2025 WebGPU overview are dated evidence, not full late-2026 certification.

**Rejected/deprioritized:** SEO compatibility lists; search summaries incorrectly saying focusMode/pointsOfInterest are not standard constraints; uncontrolled vendor/competitor performance tables; barcode sizes substituted for document engines; unrelated dataset licenses.

**Missing evidence / next steps:** physical per-phone 4K/12 MP and focus matrix; first shipped zoom/expanded-canvas/bitmap-transfer versions; present aggregate canvas/process-memory budgets; measured iPhone WebGL texture limits; current full commercial runtime transfers; complete MIDV rights. Prioritize device capture/lifecycle/memory tests for release and license review before bundling data. No browser execution or performance benchmark was performed.

**Validation limitation:** `source_check` ran for key version, camera/canvas and licensing claims. It returned passages but automated semantic assessment was unavailable; important claims were manually inspected against fetched originals. Chromium issue pages were not extractable, so historical bug information is attributed to Chrome documentation, not a verified current tracker state.
